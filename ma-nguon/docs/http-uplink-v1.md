# ESP32 → Pi HTTP v1

Canonical boundary: `http-uplink-v1.schema.json`. Root owns the provider/schema, gateway owner consumes it. RF/USB format remains `protocol-v1.md`; network wraps the existing JSON message, not raw sensor samples. No cloud/broker dependency.

POST `/api/v1/gateway/ingest`, `Content-Type: application/json`, `Authorization: Bearer <gateway token>`. Pi must explicitly enable HTTP ingestion; hardware mode only. Default configured gateway ID `gw-01`; only that ID is accepted. Gateway token is random, at least32 characters, separate from dashboard password. HTTP is for a trusted isolated LAN/WPA2 network; do not publish this port on the Internet. TLS/VPN needed for untrusted networks.

Request limits:4096 UTF-8 bytes, inner message≤512 encoded bytes, no duplicate JSON keys/non-finite numbers, version1. `message` must pass the exact decoder/CRC/flags/quality checks of `protocol-v1.md`; hardware receiver rejects SIMULATED data. `active_event_ids` contains at most32 unique valid node:boot:sequence IDs (node1..65535, boot/sequence uint32, not both0). IDs are current Gateway alarm records, including already acknowledged ones awaiting resolve.

`boot_id` is16 lowercase hex characters generated afresh for each Gateway boot; `sequence` is positive uint32, unique within that boot. Retries preserve boot/sequence and inner message. No wrap/reuse: regenerate boot ID after all pending packets are settled at sequence exhaustion. `age_ms` is elapsed time since the inner message was captured, recalculated on retries; it includes all queuing time. Current active IDs may change between retries. These two fields are excluded from the idempotency content fingerprint.

There is one in-flight HTTP request per Gateway. Allocate sequence when selecting the message for its first network send, not at RF capture; urgent priority can reorder queued messages. Pi keeps a durable per-boot high-water sequence. An unknown identity at/below that high-water returns409, including after its receipt was pruned. A known retained receipt still returns200 duplicate. Never retry an older discarded message after moving on to a newer sequence. Active IDs must be canonical decimal strings without leading zeroes.

Pi returns200 only after raw receipt, frame/event effects and dedup marker commit to SQLite. Response echoes version/gateway_id/boot_id/sequence with `accepted:true`, `duplicate:<bool>`, and up to32 `commands` from durable operator states for the IDs the Gateway advertised. A retry with the same identity/message is acknowledged without reapplying or refreshing telemetry, even after Pi restart. Reusing an identity for different message content returns409. Receipt ledger rolls at approximately100000 records; alarm dedup/operator state is independent and persists. Older telemetry may be stored as a receipt while intentionally not replacing newer live telemetry.

Response commands are `{"kind":"alarm_ack|alarm_resolve","event_id":"node:boot:seq"}`. They are idempotent and applied by the main Gateway loop to its local AlarmBook only. Do not emit a new uplink diagnostic for every repeated response command. No command is sent to the wearable. Successful transport acceptance NEVER silences a Gateway alarm: only the operator ACK/RESOLVE command does. The wearable local-clear rule is unchanged.

Gateway validates the complete response identity, accepted=true, command types/IDs, length and JSON before removing its pending packet. A malformed/mismatched200 is a failed delivery, not success. Timeouts/429/5xx retry with bounded backoff.401/403 indicate configuration/auth failure and must back off without blocking RF; invalid4xx packets are diagnosed/dropped instead of looping forever. No redirects. Network timeouts must run outside RF/main loop in a dedicated worker. Fixed-size urgent/normal queues; normal telemetry can expire/coalesce, urgent overflow increments drops and must not silence alarms. Queues are RAM-only: Gateway power loss can lose unsent history; active node snapshots can recover an alarm later but do not recover every historical sample.

Backend computes receive time as current monotonic time minus age_ms. Delayed samples and duplicate retries cannot make old vitals fresh. Malformed packets400/413/422, authentication401/403, ID conflict409, rate limit429, storage unavailable503. There is no accepted=false success. Do not log credentials or put tokens in URLs.

Time spent reading the request body on Pi is also subtracted from freshness. There is no synchronized one-way network timestamp; connection setup/transit before the first received byte remains uncertainty and must be measured in the physical latency test. Queue age is not a guarantee of exact sensor-to-screen latency.

Dashboard LAN access requires explicit allowed hostnames/IPs and a separate web password. Gateway endpoint accepts only its Bearer credential; the dashboard uses browser authentication/session. Browser Origin requests are rejected by the ingestion endpoint. USB ingestion and HTTP ingestion are mutually exclusive at runtime; firmware can keep USB output for diagnostics/bench testing.
